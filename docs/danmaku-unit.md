# 弹幕的基础单位（Danmaku Unit）

> **性质**：用户于 2026-11-04 抛出的设计观点，先于任何实现。§1~§5 只做保真记录与理解对齐。
> **状态（观点提出当时）**：观点已确立；「单个格子」是用户明确说「目前还没设计出来」的设想，**不是现状**。
> **状态更新（同日晚，v5.3）**：该设想**已实现** —— 合胞 / 晶锥的单位是单个晶胞，叠层的单位是一层；见 §6 设计登记。
> §1~§5 保留当时的原文（含「尚未设计」的措辞），§6 是后续实现，**两层时间线别混读**。
> **维护规则**：后续观点或修订追加到本文，始终保持「原话 / 理解 / 边界」三层分开 —— 别把推论写成用户原话。

---

## 1. 原话（照录，未改字）

> 弹幕是有基础单位的，而且根据招式不同，有不同的单位。
> 还是举 FCC 为例子。它很轻松就能有近千个子弹。
> 在晶格齐狙里，弹幕的单位是一个子弹。这是显而易见的
> 在晶格雨中，弹幕的单位是一层，比如 A,B,C 层
> 在某些情况下，FCC 的单位也可以是单个格子。只不过目前还没设计出来。

---

## 2. 我理解到的意思

**一句话**：一个招式不是「一堆子弹」，而是**若干个单位**组成的；单位是这个招式里被整体生成、整体调度、整体复制、整体调参的那个最小语义对象。单位**由招式决定**，不是全局常量，也不是由子弹数决定。

拆开四条：

1. **有单位，且单位随招式变。** 同一个 FCC 点阵底层，换个招式，单位就换了。所以「FCC 的单位是什么」这个问题没有单一答案，得问「哪一招的 FCC」。
2. **单位 ≠ 子弹数。** 「FCC 很轻松就能有近千个子弹」是**数量描述**，不是单位描述。一块全空间晶体实测约 940~1163 颗（HANDOVER §7.4），但按层调度时真正被数的对象只有 A/B/C 三种层、周期 3。子弹多不等于单位小 —— 两者不在一个层面上。
3. **单位是编排层的粒度，子弹始终是实体层的粒度。** 单位是「一起动作的那一组」；渲染、碰撞、积分的最小实体仍然永远是 `Bullet`。单位为「一颗子弹」时两层恰好重合，所以说「显而易见」；单位为「层 / 格子」时两层就分开了。*（这一条是我的推论，见 §4。）*
4. **单位可以尚未实现。** 「单个格子」是用户对 FCC 第三种单位的设想，明确说了「目前还没设计出来」，不能当作已有招式或已有接口写进清单。

### 三个例子的逐条对齐

| 招式 | 基础单位 | 代码里的证据 | 玩家要读的对象 |
|---|---|---|---|
| 晶格·齐狙 `latticeVolley` | **一颗子弹** | 每颗弹各带自己的 `fireAt = 0.3 + idx * 0.09`（`lattice.ts:373`），按生成序逐颗「熄灭」变成自机狙弹 —— 调度落在**单弹**上 | 下一颗 |
| 晶格·晶雨 `latticeRain` | **一层（A / B / C）** | `fccSpaceUpright` 按层 `c` 给整层共享 `dropAt = 1.2 + (cTop − c) * 1.1`（`lattice.ts:161/186`），层内所有点一起脱离下落；`s = c mod 3` 决定该层是 A / B / C 错位（`lattice.ts:175`） | 下一层 |
| （未设计） | **单个格子** | 无 —— 用户明确说尚未设计出来 | 待定 |

> 「A,B,C 层」就是 FCC 的 ABC 堆垛：相邻密排面错开 1/3 周期，每过一层都要重新找网眼。晶雨把「层」做成单位，正是让这个几何性质直接变成调度方式与读法 —— 单位是玩家读到的那个对象，不只是实现细节。

## 3. 边界：这个观点没在说什么

- 不是说子弹数量不重要，也不是在给「多少颗算一个单位」划数值线。
- 不是说每招只能有一种单位（用户未规定，暂不替他定）。
- 不是要求现在改代码或加接口。**本文是记录，不是任务单。**
- **「单个格子」不是现状**：不写进招式清单、不写进 `PATTERNS`、不写成已实现的难度旋钮。
- **术语待澄清**：「格子」在 FCC 语境里至少有两个可能 —— ①一个**晶胞**（常规立方胞：8 顶角 + 6 面心）；②一个**格位 / 网眼**。两者会导向完全不同的招式。未确认前不选定。

> **v5.3 落地注**：上面两条边界在当晚开发时已关闭 —— 用户确认「格子」= **常规立方胞（14 点，拼合时共享点去重）**，
> 并授权把单位做进代码。§3 原文保留，只作为「观点提出当时」的约束记录。实现见 §6。

## 4. 与现有四篇的关系（推论，非用户原话）

| 已有文档 | 衔接点 |
|---|---|
| `danmaku-framework.md` §3 五层语法 | 序列层目前默认把「一次 volley」当调度对象；单位概念指出：招式**内部**的调度粒度是可变的，可以是弹、层、格子 —— 这是序列层之下还缺的一层说明 |
| `danmaku-3d-taxonomy.md` §10 难度语法 | 「注意目标级别」是**认知侧**；单位是**生成 / 调度侧**。两者不同层，但单位往往决定玩家必须注意的对象（跟弹 vs 跟层） |
| `HANDOVER.md` §10 设计纪律「难度 = 参数组合」 | 旋钮拧在哪一级取决于单位：单位为弹 → 发射间隔 / 弹速 / 点距；单位为层 → 层间隔 / 层数 / 层内点距；单位为格子 → 复制份数 / 格间距。**设计新招先定单位，再定旋钮**，与「招式留参数和接口」的既有纪律一致 |

**待确认的三个问题**（不阻塞本文，等用户一句话）：

1. 「格子」是晶胞，还是格位 / 网眼？
2. 一招能否有嵌套的多级单位（例如层里再分格子）？
3. 单位是否要成为招式的显式属性（在代码 / 设计登记表里声明），还是只作为设计时的思考口径？

> **2026-11-04 晚已确认 / 已形成的结论**：
> 1. 「格子」= **晶胞**（不是格位 / 网眼），14 点/胞，8 胞拼 2×2×2 时共享角/面心去重 → 63 点；
> 2. 多级单位嵌套：**未规定**，本次三招都只用单级单位（合胞 = 胞、叠层 = 层、晶锥 = 胞）；
> 3. 单位**仍不是代码里的显式字段**，是设计时先定的口径；代码里体现为「每胞 / 每层一个 `LatticeFrame`」，
>    即**一个单位 = 一个组帧** —— 这是本次开发形成的实现约定，不是用户原话。

## 5. 一句话备忘

> **先问「这一招的单位是什么」，再问「弹放多少、怎么排」。近千发子弹的招，单位可能只有三层。**

## 6. 实现登记（2026-11-04 晚，v5.3）

> 本节是**开发记录**，不是用户原话。三招由「弹幕的基础单位」观点直接派生，全部按「先定单位 → 再定旋钮」实现。

### 6.1 三新招

| 招式 / 注册名 | 单位 | 单位数 | 生成形态 | 落位弹数 | 阶段 / holdCd |
|---|---|---|---|---|---|
| 晶格·合胞 `latticeAssemble` | **单个晶胞** | 8 | 14 点/胞（8 顶角 + 6 面心）；以原点为心的 14~20m 球壳随机 8 处召唤，0.8s smoothstep 飞到**施法瞬间锁定**的玩家位置，拼 2×2×2；8 胞共用随机 3D 朝向，定死不转 | 飞行中 112 → 拼合去重 **63**；`life=2.5s` 自行退场 | P1 / holdCd **2.5s** |
| 晶格·叠层 `latticeStack` | **一层（A/B/C）** | 6（ABC×2） | 每层「一份场地大」的密排面，从 x=−30 横扫到原点停住；层距 2.083m、层内距 2.552m（`gap=0.95`，与 FCC 几何自洽）；层间隔 1.1s；**停住后不落雨** | A 层 211 / B·C 层各 219 → **1298** | P2 / 9s |
| 晶格·晶锥 `latticeCone` | **单个晶胞** | 8（2³，由 3³ 复核降级） | 1 点爆出、锥轴锁 boss→玩家；8 方向按 1/3/4 分环（半角到约 14°）；**胞内** 14 点从一点撑到 1 个晶胞边长 3.8m（0.9s），胞间只沿各自方向直飞；所有胞 (1,1,1) 体对角线对准玩家；**弹为 `r=0.18` 正八面体**（放射锥同款，复核后从 `r=0.5` 大玉换掉） | **112** | P3 / 7s |

### 6.2 两处修正

| 招式 | 改动前 | 改动后 |
|---|---|---|
| 晶格·滑移 `latticeShear` | 两半组帧原点挂在 `boss.x/boss.z` 周边 | 组帧原点改到**场地原点** ± 偏移；裂缝法向仍朝玩家（用户选「只挪释放位」） |
| 晶格·自旋 `latticeSpin` | 旋转不变域圆盘 R=10.5 + 轴向 ±10.5 = **537 颗**，x/z 只盖半个场地 | 圆盘 R=18 + 轴向 ±18 = **2713 颗**，x/z/高度都盖满场地直径；`axis z` 晶格 y 下界 -12 → -20 配套放宽 |

### 6.3 实现约定（推论，非用户原话）

- **一个单位 = 一个 `LatticeFrame` 组帧**：合胞 8 帧、叠层 6 帧、晶锥 27 帧。单位是被整体调度的最小对象，组帧正好是整体变换的载体。
- 组帧新增 4 个**全可选**字段：`rot`（3×3 任意 3D 姿态）/ `fly`（到点 smoothstep + delay）/ `grow`（胞内撑开）/ `dedupAt`（拼合去重）；弹新增 `dedup` / `noOut`。**默认全关闭，旧 13 招零改动**。
- 弹数已按生成逻辑真跑核对：单胞 14、8 胞去重 63、晶锥 **2³=8 胞 112**（旧 3³=27 胞 378）、6 层 **1298**（A 211 + B 219 + C 219，×2；ABC 面内偏移不同 → 每层边界点数不同，不是 211×6）、自旋域 2713。
- **单位数也是绘制量的主旋钮**：3D 形状弹每颗约 78 次 canvas 调用，3³=27 胞时 ≈2.9 万/帧、真 GPU p95 182ms 卡顿；改 2³=8 胞后 8961 次/帧、mean 2.181 / p95 6.6 ms **PASS**。`ConeOpt.rings` 留了回退 27 胞的接口。
- **「等待」有两套时钟，别只改一套**：`boss.holdCd` 管对局里下一招何时抽（合胞 2.5s），
  `Bullet.life` 管晶体自己在屏幕上杵多久。原先合胞沿用全局 `LIFE=15`，训练场 `fieldBusy()` 要等场清才重放，
  实测一发后静止 15 秒、16.5s 才循环 —— 用户体感的「后半等待」在这里。现给合胞单独设 `life = 2.5s`
  （`AssembleOpt.life` 旋钮），训练场重放降到 ≈4s、晶体在场 2.5s，对局刚好接上下一招。
- 难度旋钮全留参数带默认值：`AssembleOpt` / `StackOpt` / `ConeOpt`（点距、层数、层间隔、飞行时长、锥角、弹速…）。**难度是参数组合，不是重写招式**。

### 6.4 边界

- 只改 `types.ts` / `bullets.ts` 积分 / `lattice.ts` / 四处注册表 / 文档口径；**不动渲染层、经典 38 招、L1~L3 序列**。
- 三招全进 Level 4 序列（P1/P2/P3 各一招），轮长 ≈15/44/58s；训练场 54 格、`?pat=` 全支持、分类表 54 条。
- **自旋性能**：用户复核后确认「目前还好，先这样吧」—— 2713 颗与真 GPU 单帧 FAIL 一并保留，未降级、未改点距（口径见 README「性能口径」）。
- **后续概念**：用户接着提出「招式的连接」并据此重排 Level 4（v5.4），见 `docs/danmaku-framework.md` §3.3。
  单位是「一招内部怎么组织」，连接是「两招之间怎么续接」，两者层级不同、互补。
